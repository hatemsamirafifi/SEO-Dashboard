## Integration risks for the ported items

1. **4-class fetch model** ripples: `audit_pages.fetch_class` column values, `PageFetchClass` type, blocked/rate-limited issue wording (`blocked-page` for WAF vs new issues for `rate_limited`), MCP `get_audit_pages` fetchClass filter, existing `badseo` fixture expectations (403 fixture stays `blocked`; add 429/202 fixtures). Dual-dialect column change → parity test.
2. **Throttle + window state** must checkpoint through fork's batch-step return values (existing 768 KiB/step budget): throttle state is tiny (≈60 B); window delta ≈ one integer. Safe.
3. **Window rescaling** interacts with fork's 2 MiB/page read cap: `budgetBytes ÷ avgPageBytes` bound must use the same byte accounting (fork already records sizes? — verify: fork does NOT track `htmlBytes` today; add a column or compute from body length at fetch time; worst case fall back to `MIN_ASSUMED_PAGE_BYTES`).
4. **202/2XX challenge reclassification** changes historical data semantics: new column values for future rows only; no data migration of past rows.
5. `rate_limited` retry path must honor locked decision: bounded retries (≤3/URL), 30-min max cooldown, then final classification — an exhausted 429 is _reported_, never hidden and never counted as an SEO content finding.
